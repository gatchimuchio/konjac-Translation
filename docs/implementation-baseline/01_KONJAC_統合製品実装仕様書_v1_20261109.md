### S1.1 暫定技術選定

1. 共通処理基盤はRustを施工第一候補として採用する。選定理由：ネイティブ実行、資源制御、メモリ・並行性安全、既存主要OSターゲットとWASMへの接続。Rustは製品正本、唯一許された言語、AICompiler互換性の証明ではない。
2. UI・配布基盤はTauri 2を比較基準候補とする。5 OSすべての音声・画面取得等の実能力が成立するかは機能別に監査し、適合しなければ同一契約の別アダプターを採用する。Tauri採用自体は目的化しない。
3. Web UIに必要なTypeScript等、OS固有のKotlin/Swift、C/C++音声ライブラリ、検査用Pythonの利用を許す。ただし各言語依存を製品契約へ漏出させず、使用理由・配布負債・移管条件を記録する。
4. Python 3.12の検査環境が存在しても、Python製品ランタイムの採用決定とは扱わない。
5. AICompilerへの将来移管はソースコードの自動再コンパイル保証ではない。実装を置換し、同一の外部契約・振る舞い・停止・責任・出力・監査・資源条件へ適合させる工学的移管として扱う。

### S1.2 バッファ・冗長性

1. 媒体・OS・CPU・処理場所・実装言語・伝送方式による差分は、独立した適合アダプターと公開された契約に吸収する。
2. 遅延・音声バッファ・キュー容量・再試行・永続化・断線復帰の余裕は、許容限界と測定条件を明記し、無限の猶予や暗黙の成功にしない。
3. 冗長経路は実行主体・承認・切替・出力出典を識別できる場合だけ許可する。翻訳エンジンを秘密裏に別モデルへ切り替え、MINIDORAの成功と表示することは禁止。
4. ある言語・OSの実装が破綻しても、契約と障害証拠を保ち独立して交換できる構造を成立させる。交換可能という宣言だけで同一性保証とはしない。

## S4 全体構成・責任分離

1. 正規経路：利用者／媒体→許可・取得→VAD/ASR/OCR/抽出／構造化→共通TranslationRequest→MINIDORA公開入力機→本体→出力機→結果照合→字幕/TTS/文書/画面/API→許可済み配送。
2. Konjacが所有：製品UI、媒体取得、ASR/OCR/VAD、話者・時刻・位置、権限・同意、外部通信、セッション、要求型、橋渡し、表示、TTS、成果物、版・監査・復旧。
3. MINIDORAが所有：言語の意味処理、候補採否、学習・駆動の正本、内部停止・責任境界。Konjacに第二の意味エンジン、第二の学習・最終採否機構を置かない。
4. 専用NN ASR/OCR/TTSを採用する場合は主体・版・能力・ライセンス・測定を分離する。認識・音声合成の性能をMINIDORAの翻訳能力へ算入しない。
5. MINIDORAの0.6.0b1と後継Rust/R2実装は異なる版。旧βを改変せずEnginePortで交換可能にする。公開実訳API・言語ペア・ストリーミングは現時点で未実証、実訳成立はBLOCKEDとする。
6. 比較用の第三者翻訳器は本番経路から隔離した比較モードでのみ実行し、比較結果に主体・能力・出典を表示する。成功偽装に使用しない。
7. 将来AICompilerによる置換時、製品側の共通契約と受入母集団は保つ。言語・ABI・コンパイラ固有の概念を論理正本にしない。

## S5 データ・状態・能力契約

### S5.1 必須論理レコード

| レコード | 必須意味属性 |
|---|---|
| SourceAsset | 媒体種別、元ID/指紋、所有・権利・取得許可、原データ参照、時刻・位置基準 |
| TranslationSession | セッションID、言語設定、話者・相手、処理場所、同意、状態・版・文脈参照 |
| SourceSpan | 原文、範囲、話者、時刻／文書・画像座標、ASR/OCR信頼度、出典 |
| TranslationRequest | 要求ID、入力版、原文参照、元言語候補、訳先言語集合、文脈、用語、期限・停止条件 |
| EngineExecution | エンジンID/厳密版、公開入口、能力照会、入力/応答指紋、内部終端の写像、証拠 |
| TranslationVariant | 対象言語、対応元範囲、訳文、版、暫定/確定、根拠、訂正履歴 |
| DeliveryArtifact | 字幕/音声/文書/重畳/API等の形式、送信先、権限、時刻・配置、配送状態、監査ID |

- 契約の論理的同一性を第一とし、JSON Schema/OpenAPI/Protobuf/ABIは交換可能な射影とする。11種スキーマとの先行報告は現物照合まで未確定。
- 識別はsource_asset_id/session_id/span_id/request_id/input_version/result_version/target_languageを保持。順不同到着、重複、再試行、複数訳先、機器切替で対応関係を失わない。
- 元データ・翻訳結果・ユーザー修正・確定状態は版を追加して記録。無断上書き・結果のみの保存で原文追跡を喪失させない。

### S5.2 状態契約

- 入力：CREATED／AUTHORIZED／CAPTURED／EXTRACTED／CANCELLED／FAILED。
- 認識：PROVISIONAL／FINAL／REJECTED。ASRのFINALと翻訳の確定・MINIDORA内部採否は異なる。
- 翻訳：PENDING／SUPPORTED／UNSUPPORTED／SUSPEND／FAILED／TIMED_OUT／CANCELLED／RESULT_AVAILABLE。
- 配送：PREPARED／AUTHORIZED／DELIVERED／DELIVERY_FAILED／DELIVERY_UNKNOWN／REVOKED。
- VERIFIEDではない能力をSUPPORTEDにしてはいけない。既知の非対応はUNSUPPORTED、証拠不足・判定保留はSUSPEND等の適切な型付き状態で返す。
- キャンセル要求成功≠処理停止確定。内部結果成立≠外部配送完了。重複送信や不明配送を成功へ丸めない。
- セッション・入力・出力・配送の許可は別。表示可能でも録音・クラウド送信・相手への書込を許可したとは限らない。

### S5.3 交換・移管の同一性条件

同じ仕様版・適用範囲・入力状態・権限条件に対し、実装AからB（Rust→AICompilerを含む）へ交換しても、観測対象の入出力・状態遷移・終端・失敗・版・配送許可・出典の関係が契約内に留まることを検証する。プログラム言語の文法一致・バイナリ一致は要求しない。差異を発見した場合は仕様か実装か検証条件かを分け、記録・修正する。
