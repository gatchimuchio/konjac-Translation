## C3 技術・言語の施工判断

1. 製品の論理正本は01仕様書の要求・入出力・状態・責任・品質。Rust/CPU/OS/シリアライズは交換可能な実装とする。
2. Rustを暫定共通処理基盤の第一選定とする。採用/不採用の根拠は性能・メモリ・移植性・配布・保守・再利用・各OS実機制約と現在実測で記録。理由なくPythonを製品ランタイムの正本にしない。
3. Tauri 2は全5OSアプリの共通UI候補。WebはE06の独立利用経路として同じ契約を利用。必要なTypeScript/Kotlin/Swift/C/C++等は境界付きで採用し、Tauriの未対応APIを成功扱いしない。
4. Windows/Linux/macOS/Android/iOSで本番配布可能なアプリ構成と、Webブラウザで本番利用可能な経路を全体系として設計・施工。環境により取得できない音声や画面は権限外/非対応を表現し、無断回避しない。
5. Rust固有型、ネイティブABI、Python環境、フロントエンドフレームワークを外部製品の唯一正本にしない。論理契約と技術射影を分ける。
6. 将来AICompilerへ全実装移管する条件として、同一要求・状態・停止・効果・出力・監査の適合テストを準備する。AICompilerが現時点でRustソースをそのままコンパイルできるとは仮定しない。
7. 特定技術へのロックインを減らすための必要な抽象化は許すが、実証のない過剰な汎用化・空フレームワークを施工成果としない。

## C4 全体構成を一括BUILD・結線

1. 02工程表W01-W12を全数施工対象とする。契約、許可、原文・版、入力取得、ASR/VAD、OCR、映像同期、MINIDORA橋渡し、TTS/字幕/文書/重畳/共有、セッション、各OSクライアント、Web/API、ビルド/CIを欠かさない。
2. 媒体入力→取得権限→媒体前処理→共通要求→EnginePort→MINIDORA公開入口→結果／停止→媒体出力→配送権限→実配送、という一本の製品経路を結線する。
3. U01-U12の全経路をこの同一構成へ接続。一つの翻訳仕事を複数出力・複数言語・複数端末へ展開する時は原文、話者、文脈、時刻、版、出典を維持。
4. MINIDORA実訳能力不足は型付きUNSUPPORTED/SUSPEND/BLOCKEDとして実経路に残す。機能をまだ持たないことと配線がないことを区別する。外部の別翻訳器を秘密裏に流用しない。
5. エンジンや音声モデルの有無を問わず、起動・設定・ファイル取込・データ保持・権限・不成立表示・停止・障害回復を本番と同じ経路で作る。ダミーGUI、静的成功JSON、検査用モックを本番実装としない。
6. 全構成BUILD・結線が済む前に、U単位の成功を製品完成として宣言しない。途中のコンパイル・型・セキュリティチェックは実施してよいが、個別試運転型の工程へ戻さない。
7. 外部ASR/OCR/TTS・学習済みモデル・素材を取り込む場合は版・出典・ライセンス・NOTICE・配布条件・変更箇所を監査し、認識/合成と翻訳本体の能力を混同しない。

## C5 検証・品質の実行

1. 全結線後、局所QC→全体QC→E01-E06環境別QAの順。故障時は上流の仕様・契約・実装・環境仮定まで戻して根因修正し、同一条件で再検査する。
2. 全19項目（A01-A07/U01-U12）×要求定義・実装・結線・局所QC・全体QC・環境QA・Owner受入を独立判定。PASS/FAIL/NOT RUN/BLOCKED/SUSPENDの語義を変えない。
3. 6環境の対象OS/CPU/ABI/ブラウザ・許可・モデル・処理場所・資源の検証範囲を明示。実機は最終確認として別欄に残し、未実機確認を理由に仕様適合そのものを恣意的に書き換えない。
4. 負例：権限拒否、端末音声非取得、モデル不在、未知言語、翻訳中止、通信断、重複、到着逆転、字幕版巻戻り、音声再入力、画面・文書位置誤対応、保存・配送不明、資格情報露出を含める。
5. 受入データに実際の英⇄日、長文、曖昧表現、固有名詞、複数話者、別言語対照、原文比較を含める。ただしエンジン実訳未成立ならその項目をBLOCKEDのままにする。
6. 性能は端末・入力・処理段階・サンプル母集団を固定して計測。根拠なしの閾値生成、他社性能の転用、数値なしの「高速」宣言は禁止。
7. 自動テスト・CIの成功を製品実訳の成立へ昇格しない。過去の313件のMINIDORA選択テストはその当時のβ境界の証拠であり、Konjac実訳の証拠ではない。
8. 保留・未実施・重大リスクが残ればその事実を正本に保持する。合格条件の変更や失敗の削除で帳尻を合わせない。

## C6 保存・復旧・変更履歴

1. 作業前に未コミット差分を保護し、他環境へ引継ぎ可能な形で履歴を残す。ユーザー既存変更・第三者変更を上書き/削除しない。
2. Gitのコミットは実際の差分と根拠を保持する復旧単位であり、施工ゲート・受入証拠ではない。各変更の開始HEAD・終了HEADを明示。
3. 旧判断はDECISIONSへ追記型で変更理由・元版・影響・採用/却下を記録。既存文書を整合修正しても履歴の原意を改変しない。
4. Cloud環境のPython仮想環境や一時キャッシュは再現可能な依存固定・実行手順へ落とす。保存/公開されていない環境設定を次回利用可能と断言しない。
5. リポ公開範囲に秘密、個人音声・私信、非公開HDS、外部資格情報、ライセンス未確認モデルを残さない。

## C7 停止・報告境界

Owner判断が必要なもの：製品目的/母集団の実質変更、責任境界の変更、凍結MINIDORA改造、公開HDS範囲、権利不明の大規模ソース移植、第三者への送信・契約、本番公開・正式リリース。

Owner判断が不要な通常施工：対象リポ内のコード・テスト・設計整合修正、適切な技術比較、許可された依存取得、CI/ビルド、仮想検査、復旧可能なコミット。ただし上位の明示的権限・安全制約は保持する。

判定に必要な資料を取得できない場合はUNKNOWN/NOT RUNとし、依存が独立した作業を止めない。対象や保持条件が不明な破壊的操作は実施しない。

## C8 必須提出物・終了条件

1. CURRENT：開始HEAD、終了HEAD、変更ファイル、追加/更新/保留、競合、使用環境・依存版。
2. COVERAGE：W01-W12、A01-A07、U01-U12、E01-E06の全数トレース。実装・結線・QC・QA・Ownerの各状態を分離。
3. ENGINE：MINIDORA厳密版、実在API、能力一覧、実訳成立/不成立、独立変更要求、後継実装交換境界。
4. PORTABILITY：Rust共通基盤、OS/ブラウザ別アダプター、Python/TypeScript/Kotlin/Swift/C++依存、AICompiler移管時の交換対象と同一性試験。
5. EVIDENCE：テストコマンド、入力、期待・観測、時刻、OS/CPU/ブラウザ、ログ/アーティファクト、FAIL・NOT RUN・BLOCKEDの根拠。
6. SECURITY：許可、外部送信、保存・削除、第三者ソース、ライセンス、HDS公開境界の監査。
7. DECISIONS：確定判断、未決議題、採否根拠、Owner判断要求。
8. STATUS：全体実装完成か、品質成立か、翻訳製品成立か、公開可能かを別々に記述。根拠のない完成率を記述しない。

最終命令：製品の全数母集団を保持し、全体系を構築・結線した後に局所QC・全体QC・環境別QAを行う。実訳API未成立や環境未適合は失敗/保留として正確に残す。Ownerの独立最終判断を受けるまでは製品受入・公開を確定しない。
